# Testing

There are four layers:

1. **Unit and integration tests** (`npm test`, Vitest in Node): capture, storage, ingest, realtime decoding, correlation, findings, server tracer, import/export, recording control.
2. **UI component tests** (`npm test`, Vitest + Testing Library in jsdom): filters, sorting, empty states, the JSON viewer, dialogs, keyboard, theme, a 50,000-row list.
3. **End-to-end tests** (`npm run test:e2e`, Puppeteer + Chrome): five suites load the real built extension in Chrome and drive local test pages, a realtime test server and a real Next.js app.
4. **Manual verification** in your own Chrome, for what automation can't reach (section 4).

Run everything except E2E with:

```bash
npm run check   # typecheck + lint + unit/UI tests + build
```

## 3. End-to-end tests (real Chrome)

```bash
npm run test:e2e              # all five suites, headless
npm run test:e2e:realtime     # one suite
npm run test:e2e:ssr          # needs `npm install` in examples/next-ssr (skips itself otherwise)
HEADFUL=1 npm run test:e2e    # watch it run (PowerShell: $env:HEADFUL=1; npm run test:e2e)
```

By default, Puppeteer uses its own Chrome for Testing, downloaded on `npm install`. To use an installed Chrome instead (for example, if the download is blocked or was skipped), set `CHROME_PATH`:

```powershell
$env:CHROME_PATH = 'C:\Program Files\Google\Chrome\Application\chrome.exe'; npm run test:e2e
```

```bash
CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" npm run test:e2e
```

`npm run build:e2e` produces `dist-e2e/`: the normal build plus `host_permissions: ["http://127.0.0.1/*"]`, so no permission prompt has to be clicked. It is for automation only. What automation cannot verify, and must be checked by hand: the real permission prompts (site access, `cookies`, `browsingData`), opening the popup by clicking the toolbar icon (the suites open it with `triggerExtensionAction`), the DevTools panel, and dismissing Chrome's "being debugged" banner (the detach path is unit-tested with a simulated `canceled_by_user`).

### Known timing sensitivity

- `next dev` can render a page more than once, and React StrictMode runs effects twice in development (two `POST /api/orders` per page load). The SSR checks therefore select spans by the trace id in the page's meta tag and wait for a _completed_ client request.
- Socket.IO completes its transport upgrade whenever the probe returns, before or after `connect`, with or without the extension. The behavior-comparison check compares upgrades by count, not position.
- The dashboard re-renders while data arrives. UI checks find and click a row in one step and retry until the detail shows it.
